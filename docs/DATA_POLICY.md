# Data policy

The project's README requires that training data have identifiable sources, recorded permissions and a review of applicable obligations, and excludes NonCommercial and NoDerivatives restrictions. This document states how those requirements are applied. The rules are enforced in code by [`slm.data.registry`](../src/slm/data/registry.py), and `python -m slm sources audit -v` shows the result for every declared source.

This policy is an engineering gate, not legal advice. Passing it means the recorded facts meet the project's rules; establishing those facts remains the reviewer's responsibility.

## Source lifecycle

1. **Declare.** Add the source to [`configs/data/sources.yaml`](../configs/data/sources.yaml) with its URL, the license declared by its publisher, role (`pretrain`, `posttrain`, `eval`, `tokenizer`) and status `candidate`. Write the open questions a reviewer must answer.
2. **Pin.** Record the exact revision (dataset commit hash or release tag). Without a pinned revision a source cannot pass the policy.
3. **Review.** A reviewer checks provenance, the license of every component actually used (`component_licenses` for aggregated collections), and privacy risks, then records the outcome, their name and the date in the `review` block.
4. **Approve.** Set `status: approved`. The audit fails if an approved source does not satisfy the policy, so the registry cannot drift from the rules.
5. **Use.** The data pipeline refuses unapproved sources. `--allow-unapproved` exists for exploratory runs only and is written into the pipeline manifest, so such data can never be mistaken for the core corpus.

## License rules

| Category | Licenses | Treatment |
|---|---|---|
| Permissive | CC0-1.0, public domain, PDDL-1.0, MIT, BSD-2/3-Clause, Apache-2.0, ISC, Unlicense, CC-BY-3.0/4.0, ODC-By-1.0, Licence-Ouverte-2.0 | Allowed; attribution recorded where required |
| Share-alike | CC-BY-SA-3.0/4.0, ODbL-1.0, GFDL-1.3 | Allowed; the obligation is listed in the release documentation |
| Restricted | Anything containing NonCommercial or NoDerivatives terms | Excluded |
| Unknown | Anything else, `mixed` without components, `other` | Blocked until reviewed and added explicitly |

A dataset-level license does not settle the status of the content inside it. Web-crawl compilations under ODC-By license the compilation, not the pages, and are therefore `comparison-only`: they may serve as quality baselines in labelled runs but never enter released weights. The registry uses `component_licenses` for licenses of components actually used and `license_options` for alternative licenses declared for the same source. Post-training sets generated by other models need the terms of the generating model recorded for each subset.

## Processing record

Each pipeline run writes, next to its output:

- `manifest.json`: resolved configuration and hash, input file hashes, the policy decision for each source, evaluation files used for decontamination, output hashes, code revision and software environment;
- `decisions.jsonl`: one line for each removed document, with the step, the reason and details such as the document it duplicates;
- `stats.json`: counts per step, reason and source.

Every kept document carries its source, source revision, original identifier, declared license and the SHA-256 of its original text, so any training token can be traced back to its source document.

Token shards record the tokenizer hash and the hashes of their inputs; the training run manifest records the shard hashes. Together these files connect released weights to the exact documents that produced them.

## Privacy

The `pii` step replaces email addresses, public IPv4 addresses, phone numbers and IBANs with placeholders and counts replacements. Pattern matching does not detect names or free-text personal information. Each source therefore also needs a privacy review (`review.pii_reviewed`) that considers what the source contains and how it was collected.

## Benchmark contamination

Every evaluation set used in reported results is listed in the `decontaminate` step of the pipelines that produce training data. Documents sharing a 13-gram with an evaluation item are removed, and the matched items are logged so contamination can be reported per benchmark. Evaluation sets used to tune agent environments are kept separate from final evaluation sets.

## Synthetic data

Synthetic records carry the generator name and version, seed and parameters. Records produced with a teacher model must also record the model identifier and revision, its output terms, the prompts or templates, sampling settings and the verification procedure. Teacher outputs are subject to the license rules above like any other source.

## Releasing data

A data release includes the manifests and a data card ([template](templates/DATA_CARD.md)). Where redistribution of the processed text is permitted, it is released; where only the recipe can be shared, the manifests and scripts let others rebuild the same corpus from the pinned sources.
